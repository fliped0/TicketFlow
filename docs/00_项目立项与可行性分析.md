## 1. 项目概述

### 1.1 项目名称

**TicketFlow —— 高并发智能票务平台**

### 1.2 项目定位

TicketFlow 面向演唱会、音乐节、展览和体育赛事等活动场景，提供活动浏览、场次与票档查询、抢票、订单、模拟支付、取消和退款等核心票务能力。

项目以 Java 后端工程能力为主线，重点实践高并发场景下的库存、订单、缓存、消息和一致性设计；核心系统稳定后，再通过独立 AI 服务接入大语言模型、RAG 和工具调用能力，形成智能票务 Agent。

### 1.3 项目性质

本项目同时具备三重属性：

- **工程项目**：按照规范的软件工程过程完成需求、设计、开发、测试、部署和优化。
- **学习项目**：每项技术都由实际问题驱动，并完成设计与代码复盘。
- **求职项目**：沉淀可量化的性能实验、架构演进依据和可清晰表达的面试材料。

## 2. 项目背景与问题定义

热门演唱会或体育赛事开票时，系统可能在短时间内承受远高于日常流量的并发请求。例如：

- 总票数：10,000 张；
- 同时访问用户：100,000 人以上；
- 热门票档库存：2,000 张；
- 大量用户在数秒内集中提交抢票请求。

若仅依赖应用服务直接访问 MySQL 并同步完成库存扣减和订单创建，容易出现：

- 数据库连接和写入压力过大；
- 并发竞争导致库存超卖或少卖；
- 用户重复提交产生重复订单；
- 请求长时间阻塞，响应显著变慢；
- 局部故障扩散并引发系统雪崩；
- Redis、MySQL 和消息队列之间的数据一致性难以保证。

TicketFlow 将先实现最小可运行的基础业务，再通过测试暴露瓶颈，逐步引入 Redis、Lua、消息队列、幂等、限流和延迟任务等机制，并用数据验证每次改造的实际效果。

## 3. 项目目标

### 3.1 业务目标

实现完整、可运行、可测试的票务核心流程：

```text
注册 / 登录
    ↓
浏览活动
    ↓
查看场次与票档
    ↓
提交抢票请求
    ↓
创建订单
    ↓
模拟支付
    ↓
查看、取消或申请退款
```

管理员能够创建和维护活动、场次、票档、价格与库存，控制活动上下架，并查看订单数据。

### 3.2 技术目标

围绕实际业务问题，分阶段实践以下能力：

- 使用 Java、Spring Boot、Spring MVC 和 MyBatis-Plus 构建后端 API；
- 使用 MySQL 事务、索引和乐观锁保证核心数据的正确性；
- 使用 JWT 完成身份认证和基础权限控制；
- 使用 Redis 完成热点缓存、库存预扣、资格校验和限流；
- 使用 Lua 保证 Redis 内多步库存操作的原子性；
- 在确有需要时使用 Redisson 或其他机制处理分布式互斥；
- 使用 RocketMQ 或 RabbitMQ 完成流量削峰、异步下单和超时处理；
- 设计幂等、补偿和一致性校验机制；
- 使用 Docker 和 Linux 完成可重复部署；
- 通过接口、集成、并发和性能测试量化系统行为。

### 3.3 工程与学习目标

- 完整经历“立项—需求—设计—开发—测试—部署—优化—复盘”的软件工程过程；
- 保持需求、设计、实现和测试之间的可追踪关系；
- 对关键技术明确记录引入原因、收益、限制和替代方案；
- 形成一套可以独立演示、部署并在面试中清晰说明的项目成果；
- 后期接入 Python、FastAPI、LLM API、RAG、Function Calling、Agent 和 MCP 等能力，但不影响 Java 核心业务的独立运行。

## 4. 用户与相关方

### 4.1 普通用户

第一版普通用户可以：

- 注册和登录；
- 浏览活动；
- 查看场次和票档；
- 提交抢票请求；
- 创建并支付订单；
- 取消待支付订单；
- 查看个人订单；
- 在符合规则时申请退款。

### 4.2 管理员

第一版管理员可以：

- 创建和修改活动；
- 发布、上架或下架活动；
- 创建和维护场次；
- 创建票档并设置价格和库存；
- 查看订单及基础统计数据。

第一版仅区分普通用户和管理员，不建设复杂的组织与权限体系。

### 4.3 项目开发者与维护者

负责需求确认、架构设计、编码、测试、部署、运行观察、性能优化和文档维护，并确保系统实现与已基线文档一致。

## 5. 项目范围

### 5.1 第一版范围

第一版包含以下核心模块：

```text
用户系统
    ↓
活动系统
    ↓
场次系统
    ↓
票档系统
    ↓
库存系统
    ↓
订单系统
    ↓
模拟支付
```

第一版最重要的端到端链路为：

```text
用户 → 活动 → 场次 → 票档 → 抢票 → 订单 → 支付
```

### 5.2 暂不纳入第一版的功能

为控制项目规模，以下能力暂不实现：

- 真实的支付宝或微信支付；
- 地图和路线服务；
- 实名认证、身份证核验和短信验证码；
- 复杂的座位图及在线选座系统；
- 黄牛识别和复杂风控模型；
- 个性化推荐算法；
- 微服务拆分；
- Kubernetes 编排；
- 真实第三方票务平台接口。

这些能力只有在核心业务稳定、需求明确且能够产生实际学习或工程价值时，才进入后续迭代。

## 6. 初步系统方案

### 6.1 架构形式

项目第一阶段采用**前后端分离 + 单体后端架构**：

```text
              Web / 前端
                  │
                  ↓
             Spring Boot
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
     MySQL      Redis       MQ
```

其中 Redis 和消息队列按照迭代需要逐步引入，初始版本可以仅使用 Spring Boot 与 MySQL。

### 6.2 组件职责

#### 6.2.1 Spring Boot

提供 HTTP API，承载认证、参数校验、业务编排、事务控制、异常处理和外部组件集成。

#### 6.2.2 MySQL

持久化用户、活动、场次、票档、库存、订单和支付记录等核心业务数据，是业务事实数据的主要存储。

#### 6.2.3 Redis

根据实际性能需求承担热点活动缓存、票档库存、抢票资格、限流计数和必要的分布式协调。

#### 6.2.4 消息队列

根据并发与异步处理需求承担异步创建订单、流量削峰、订单超时处理和后续通知任务。

#### 6.2.5 AI 服务

后期以独立服务接入 TicketFlow Java API，承载 RAG、工具调用和 Agent 编排。AI 服务不得绕过核心后端直接修改订单和库存数据。

## 7. 架构演进原则

### 7.1 问题驱动

项目不在初始阶段一次性加入全部中间件，而按照以下逻辑演进：

```text
实现基础业务
    ↓
建立正确性测试与性能基线
    ↓
通过测试发现问题
    ↓
分析瓶颈和根因
    ↓
选择最小可行的改进方案
    ↓
验证正确性、性能和复杂度变化
```

例如，先以 MySQL 完成库存扣减；若并发测试证明数据库成为瓶颈，再引入 Redis；若 Redis 中多步操作存在竞争，再引入 Lua；若同步下单无法吸收峰值流量，再评估消息队列。

### 7.2 单体优先

前期不采用微服务。先在结构清晰的单体应用中完成业务闭环和并发设计，只有当模块边界、独立扩缩容或团队协作产生明确拆分需求时，才评估服务化。

### 7.3 正确性优先

库存、订单和支付相关改造必须先满足不超卖、不重复下单、状态可追踪和异常可恢复，再比较吞吐量与响应时间。性能提升不得以牺牲业务正确性为代价。

## 8. 可行性分析

### 8.1 技术可行性

- **Java / Spring Boot**：生态成熟、资料完善，适合构建业务 API 和工程化后端，技术可行。
- **MySQL**：符合用户、活动和订单等强关系型数据的持久化需求，技术可行。
- **Redis**：适合热点缓存、高并发库存和限流场景，技术可行。
- **消息队列**：适合异步下单、削峰和延迟处理，但需要额外解决消息可靠性与幂等，技术可行。
- **Docker**：可以统一应用与依赖组件的运行环境，降低部署差异，技术可行。
- **AI Agent**：可以通过独立 Python/FastAPI 服务和稳定 API 接入，不阻塞 Java 主线，技术可行。

### 8.2 经济可行性

项目可优先使用开源框架和本地容器环境完成开发与测试。除后期可选的云服务器、域名或大模型 API 外，无强制的大额成本，经济上可行。

### 8.3 运行可行性

普通用户和管理员的操作流程清晰，第一版不依赖真实支付、实名核验或第三方票务平台，能够在本地或测试环境独立演示，运行上可行。

### 8.4 进度可行性

项目通过阶段文档和小步迭代控制范围，每次只完成可验收的模块。高并发和 Agent 能力均建立在基础业务稳定之后，进度风险可控。

### 8.5 综合结论

TicketFlow 在技术、成本、运行和迭代安排方面均具备可行性，同意立项并进入阶段 1：需求分析。

## 9. 主要风险与应对策略

| 风险编号 | 风险 | 可能影响 | 应对策略 |
| --- | --- | --- | --- |
| RISK-001 | 项目范围持续扩大 | 核心链路无法按阶段完成 | 固定第一版边界，新增功能进入后续迭代评审 |
| RISK-002 | 为使用技术而引入技术 | 架构复杂、难以解释和维护 | 先建立问题与数据证据，再决定是否引入组件 |
| RISK-003 | 代码可运行但缺乏理解 | 无法独立调试或面试表达 | 每个模块完成设计复盘、代码复盘和替代方案比较 |
| RISK-004 | 文档与实现脱节 | 设计失去指导和验收价值 | 将文档回写纳入每阶段完成标准 |
| RISK-005 | 并发场景数据不一致 | 超卖、重复订单或支付状态错误 | 建立正确性测试、幂等机制、对账与补偿策略 |
| RISK-006 | 中间件增加运维负担 | 环境难以启动、故障难定位 | 使用 Docker 固化环境，逐项引入并补齐日志与监控 |
| RISK-007 | Agent 越权或错误调用 | 查询泄露或误操作订单 | Agent 只通过受认证的 Java API 操作，并设置权限与确认机制 |

## 11. 预期成果

### 11.1 可运行的 Java 后端

至少包含 Spring Boot、MySQL、Redis、消息队列和 Docker，并能独立完成票务核心业务闭环。

### 11.2 完整的软件工程文档

至少覆盖需求、架构、数据库、API、状态机、核心流程、测试、部署、性能优化和 Agent 扩展设计。

### 11.3 可复现的性能实验

对比以下代表性方案：

```text
MySQL 直接扣库存
        VS
Redis 库存方案
        VS
Redis + Lua + MQ 方案
```

重点记录吞吐量、平均响应时间、P95、P99、错误率、数据库压力、库存正确性和订单一致性。具体目标值在需求分析与性能测试计划中确定。

### 11.4 智能票务 Agent

后期 Agent 至少支持活动查询、个人订单查询、退票规则问答，以及在认证和确认机制保护下调用 TicketFlow 后端 API。

### 11.5 项目总结与面试材料

能够基于真实设计和实验结果说明项目架构、高并发库存、Redis、消息队列、幂等、一致性、MySQL 优化、性能改造与 Agent 集成。
