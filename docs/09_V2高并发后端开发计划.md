# TicketFlow V2 高并发后端开发计划

## 1. 目标与已确认决策

- 文档日期：2026-10-06。
- 目标：为 Java 后端实习准备一个能够运行、解释、验证并独立修改的高并发票务项目。
- 学习投入：每周 10～15 小时；投递时间尚未确定，按里程碑验收。
- 技术主线：沿用 Java 17、Spring Boot、JdbcTemplate、MySQL 与现有统一分层，引入 Redis、Lua、RabbitMQ。
- V2 必做：目录缓存、入口限流、原子预占、可靠异步下单、恢复与对账、对照压测、云端部署、项目复盘材料。
- Agent、真实支付、微服务拆分、Kubernetes、多机高可用、完整前端不纳入本轮。
- 本机编写代码，云端运行中间件，通过受控连接调试；最终应用部署到云端。实际实例规格、费用与访问凭据在环境准备阶段落实，不在本计划中假定已经购买。
- 每阶段实行“实现 → 测试 → 讲解 → 独立完成一个小改动 → 验收”。

本计划用于开发与学习排期，不代表以下功能已经实现。业务选择已经通过讨论确定；异步协议须在批次 6 形成可审查的详细设计，随后再编码。

## 2. V1 基线与演进边界

工作仓库为 `D:/develop/TicketFlow`。截至现有批次 5 报告，V1 已完成用户、目录、订单、模拟支付退款、关单、管理统计与对账；报告记录 73 项测试通过，以及三轮每轮 1,000 用户、100 工作线程、100 张票的正确性实验。本轮规划没有重新运行这些实验。

现有 20 线程测试记录下单 P95 70.906 ms、支付 P95 69.325 ms；应用、数据库和负载器同机。这些数据不是系统容量上限，也没有证明数据库已经成为瓶颈。V2 首先补充逐级加压和资源观测，再进行同环境对照。异步方案作为已明确的学习目标实施，即使收益有限，也保留真实结果和原因。

普通场次继续同步下单，指定热门场次采用异步抢票。模式以场次为单位，所有票档一致；仅允许未开售、无订单、无在途请求时配置，开售后不在线切换。旧同步接口遇异步场次应明确拒绝并指向新入口，不能将原有“201 已建单”悄悄改成“202 已受理”。

现有 Flyway 历史迁移、测试证据保持不变，新结构使用后续迁移编号。业务版本 V2 与 Flyway 的迁移编号不是同一概念。

## 3. 业务规则与技术方案

### 3.1 缓存与限流

目录缓存只用于公开查询；订单、支付、退款、管理员查询及交易校验仍以数据库为依据。第一步缓存稳定的目录内容，实时库存与时间相关的 saleStatus 单独计算或刷新，不让缓存结果决定能否下单。列表分页及筛选参数纳入键设计，缓存具备版本、TTL、空结果短缓存和热点回源合并。

管理员变更提交后失效缓存，处理失效失败与旧查询回填的竞争。Redis 不可用时目录查询在并发额度内回源，额度耗尽时明确拒绝，避免无上限压垮数据库。具体 TTL 和额度作为配置，基线实验后记录其选择依据。

抢票限流按用户和场次控制，查询结果接口设置独立额度。超限返回 429 和重试提示；售空、限购、限流、系统异常分别计数。已受理请求的幂等重试和结果查询不能因普通抢票额度耗尽而失去恢复途径。Redis 故障时暂停异步新受理，普通场次维持自己的数据库链路。

### 3.2 异步受理与订单接口

新增受认证的异步提交与本人结果查询接口，建议分别为 `POST /api/v1/purchase-requests` 和 `GET /api/v1/purchase-requests/{id}`。提交包含票档、一张票的数量以及 Idempotency-Key；用户身份来自认证上下文。

- 202 仅表示请求已可靠记录，结果可能成功，也可能明确失败。
- 返回稳定请求编号和当前处理状态；成功后可查询订单编号，失败后可查询业务原因。
- 同键同参数复用原请求，不重新排队；同键异参数返回冲突。他人请求与不存在统一按 404 处理。
- 新的异步请求状态与旧订单状态分离。旧订单仍沿用 PENDING、PAID、CANCELLED、CLOSED、REFUNDED。
- 排队中占用同场次购买资格，不能换票档重复抢；本轮不提供排队撤回，建单成功后可走原取消接口。
- 建单时重新检查账号、活动上下架、售票时间、处理期限和数据库库存。下架或停售后不继续创建新订单。
- 正常情况下以可靠受理后 30 秒内得到终态为目标；受理时持久化建单截止时间，不能超过停售与开场边界。超过截止时间后禁止再建单，恢复时明确失败并释放。
- 客户端等待超时、数据库提交结果未知、处理租约超时，都不能单独作为“订单没有创建”的证据。
- 支付期限从实际建单检查时间计算，最多 15 分钟且不超过开场时间，沿用现有规则。

### 3.3 一致性与 RabbitMQ

采用“Redis 快速预占 + MySQL 持久受理记录与事务发件箱 + RabbitMQ 幂等消费”的方案。数据库保留最终订单、库存及受理状态的事实，Redis 是可核对、可恢复的预占视图。可靠受理仍需要数据库写入；压测必须计算这部分成本。

1. Redis Lua 原子执行余量检查、请求去重及同场次预占；预占关联稳定请求编号和唯一令牌。
2. 数据库事务落下受理记录、在途资格及待发送事件，提交后才能返回 202。
3. 发件箱发布器发送持久消息，使用发布确认和不可路由检测；发送成功但标记失败可能导致重复投递，由消费者幂等解决。
4. 消费者通过现有分层与明确的锁顺序创建订单；订单、库存、资格迁移、受理终态及后续事件在一个数据库事务中提交，再确认消费。
5. 业务拒绝记录终态并安排预占释放；系统故障采用有限退避重试，达到阈值进入死信处理和告警，恢复扫描仍追踪未终结受理记录。
6. 取消、关单、退款与失败释放都要可靠同步到 Redis；每条变更有事件编号和去重依据，禁止重复回补。

批次 6 必须把以下窗口画成时序图并写出状态转移及锁协议：Lua 成功但数据库未提交、数据库提交结果未知、消息已入队但发送标记未提交、订单已提交但消费确认丢失、补偿与原请求并发恢复、旧消息在恢复重建后再次到达。尤其要明确预占令牌的失效与隔离机制，避免一边释放、一边仍能提交成功。

当前 tf_request 不支持把已提交 PROCESSING 当作长期排队；tf_purchase_slot 又必须关联真实订单。因此新增独立异步请求及在途资格模型，由同一用户／场次锁协议协调在途资格与订单资格，不能只靠两个表各自的唯一键。原订单库存流水不直接记录尚未创建订单的预占。

Redis 数据丢失或需要重建时，暂停相关异步场次的新受理，并协调消费者及库存回补，基于数据库订单、在途请求和事件进度完成一致快照重建后再开放。不能发现 Redis 无库存键就直接把数据库 available 全部放回可抢池。

库存对账新增在途预占、重复回补、孤立预占和事件处理进度检查。异步受理不会消除数据库库存的条件更新与非负校验。

## 5. 测试与量化验收

### 5.1 正确性与故障恢复

- 回归全部 V1 功能；每个新增状态转移同时验证允许路径、拒绝路径和数据副作用。
- 重复请求、不同键并发、同场次跨票档、重复消息、消费者重启、支付取消退款与回补竞争均不产生超卖或重复有效资格。
- 三轮每轮 1,000 个不同用户、100 个工作线程、100 张票，无取消退款干扰；限流拒绝独立记录并按规则重试，最终恰好 100 个有效订单。
- 覆盖 Redis、MQ、数据库短时不可用，应用提交前后退出，HTTP 响应丢失，发布确认丢失及消费确认丢失。
- 正常情况下受理后 30 秒内获得可查询终态；故障实验的 100 个在途请求在依赖恢复后 60 秒内收敛，不收敛产生可定位告警并判定该验收未通过。
- 失败、重启和重复扫描之后，对账均检查订单、库存、在途资格、订单资格、预占与回补，不能只检查接口返回值。

### 5.2 性能实验

云端先固定 CPU、内存、存储、组件版本、JVM、连接池、消费者并发和资源限制。本机压测器与云端服务分离，同时记录网络和压测器资源；本机连接云端依赖的日常调试数据不作为最终性能结论。

V1 同步、缓存／限流阶段、完整异步三种方案使用同一云环境和等价数据。逐级增加 20、50、100、200 个工作线程，遇到持续积压、错误或资源饱和时停止继续加压并保留失败数据。每个用于比较的负载点预热 60 秒、测量 300 秒、至少独立重复三轮；业务身份与库存足够，避免限购或售空掩盖处理能力。

分别报告：请求发起量、受理量、最终建单量、售空／限购／限流量、系统异常、HTTP P95/P99、端到端建单 P95/P99、积压量与排空时间、数据库锁与连接池等待、各组件 CPU／内存。受理接口很快或大量拒绝不能当作成功建单吞吐提升。

性能目标在批次 6 基线后、优化实施前记录并冻结，禁止看完结果后倒推目标。沿用需求中的查询 P95 ≤500 ms、同步下单／支付 P95 ≤1 s、系统异常率 <1% 作为相应基线；新增异步以最终完成量和处理期限评价。预设提升比例尚无硬件和基线依据，不在本计划捏造“提升数倍”或“万级 QPS”。未达到改进目标时记录原因并修订方案，功能完成与性能目标未达成分别报告。

### 5.3 部署与运行

采用单机学习演示环境，容器或进程资源明确限额；MySQL、Redis、RabbitMQ 与管理面仅通过内网／受控隧道访问。公网入口配置 HTTPS；应用异常退出可恢复，日志轮转、密钥配置、磁盘空间与消息积压可检查。测试与演示使用独立数据库、Redis 命名空间／实例及 RabbitMQ 虚拟主机和队列。

备份必须在隔离数据库实际恢复并核对，不以“生成备份文件”代替恢复验收。破坏性故障实验不对演示数据执行。单机演示不宣称生产高可用，也不把数据盘永久丢失纳入自动恢复承诺。

## 6. 文档、证据与简历产出

沿用原有编号和标题层级，V2 增量进入现有需求、总体设计、详细设计、测试、部署、性能文档，不覆盖历史验收事实。本计划使用编号 09，避免挤占 07 Agent 设计与 08 项目总结。

每批交付更新接口文档与开发进度；新测试证据按日期和批次独立存放，包含运行命令、环境、代码版本、原始结果及失败记录。关键设计记录选择、替代方案、成本与验证结论。

最终简历材料围绕三类事实组织：

1. Redis 缓存／限流如何降低具体负载下的数据库压力。
2. Lua、持久受理与 RabbitMQ 如何支持异步抢票，以及重复／失败时如何保证业务一致。
3. 在指定资源、数据与负载下测得的吞吐、延迟、恢复时间及正确性结果。

实际数字完成实验后填入。使用过组件不写成精通；没有收益的数据也用于解释适用场景与代价。最后补充 RabbitMQ 与 RocketMQ 的选型对比，V2 只实现 RabbitMQ。
