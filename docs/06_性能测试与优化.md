## 1. 环境与方法

用户确认以当前 Windows 本机验收，保留既定指标。CPU 为 Intel Core i7-1195G7 @ 2.90GHz、4 核 8 逻辑处理器；系统物理内存 16,952,647,680 字节。SSD 型号 311CD0512GB，容量 512,110,190,592 字节。应用、MySQL 和 Python HTTP 负载器同机；本轮没有容器 CPU 或数据库内存限额，不代表独立服务器或生产容量。

Java 17，Spring Boot 4.1.1，MySQL 8.0.45，应用 JVM `-Xms256m -Xmx512m`，Hikari 最大连接数 20。MySQL innodb_buffer_pool_size=134,217,728 字节、max_connections=151、innodb_flush_log_at_trx_commit=1、sync_binlog=1。应用使用独立复制后的可执行 jar、一次性测试密钥及专用 ticketflow_test / tf_test；性能阶段直接连接数据库，关闭自动到期调度。组件与包哈希见[批次 5 证据](assets/04/20261004-batch5/summary.md)。

使用 scripts/batch5-experiments.py 的真实 HTTP 闭环负载。每阶段 20 工作线程、预热 60 秒、测量 300 秒；注册、登录和数据准备不计时。P95 使用逐请求延迟的最近秩法，包含客户端 HTTP 与响应 JSON 读取。开始时间落在测量窗口内的请求才采样，不用服务端日志耗时代替端到端耗时。

DATA-PERF 新建 1,000 活动、3,000 场次、9,000 票档，票档库存充足；既有测试数据保留。查询轮转活动列表、活动详情、场次和票档；活动列表过滤本轮唯一城市标记。交易给各线程独立用户及场次，成功支付后全额退款释放资格，以持续满足购买条件。退款施加真实业务负载，但不混入下单、支付的延迟样本；因此不能将这里的单接口吞吐当作纯下单峰值吞吐。

| 活动详情 | 55,016 | 55,016 | 39.676 | 22.538 | 183.387 | 0 |
| 场次列表 | 55,017 | 55,017 | 40.974 | 24.223 | 183.390 | 0 |

所有测量请求成功，业务拒绝与系统异常均为零。四项查询 P95 ≤ 500ms，下单与支付分别 P95 ≤ 1,000ms，系统异常率 <1%，本机基线通过。两个交易样本数略有差异来自预热和结束边界，不能据此认定支付丢失；全量循环结束后已独立核对全部 20 个交易票档。

最终包查询阶段运行 360.650 秒，交易阶段 405.654 秒；两者均预热 60 秒、测量 300 秒，交易总耗时还包含样本保存与逐票档对账。最终包与完整回归所用 jar 相同，原始样本重新计算后与报告一致。

保留首轮性能结果 performance-initial.json：活动列表 P95 46.875ms、下单 72.763ms、支付 70.967ms。首轮交易总耗时 1,106.023 秒包含采样后的慢对账；慢查询已修正。两轮数据保留各自包哈希与时间，不将其当作严格的优化前后性能对照。

## 3. 争票正确性

1,000 个独立用户、100 工作线程争抢单票档 100 张票；事先真实注册登录，不混入计时。自动关单禁用，每轮独立新票档，无取消或退款干扰。线程峰值为 100，不能称为“1,000 并发”。

| 轮次 | 初始请求发起跨度（s） | 收敛耗时（s） | 成功 / 售罄 | 系统错误 | 总尝试 |
| --- | ---: | ---: | --- | ---: | ---: |
| 1 | 9.245 | 10.182 | 100 / 900 | 0 | 1,000 |
| 2 | 8.676 | 9.605 | 100 / 900 | 0 | 1,000 |
| 3 | 8.446 | 9.386 | 100 / 900 | 0 | 1,000 |

三轮均在 10 秒内发起全部初始请求，60 秒内收敛；最终恰好 100 个订单、可售库存为零、占用 100、无超卖、重复资格或孤立记录。争票验证正确性，不用于宣称交易接口性能 SLA。

## 4. 发现与优化

大样本最终对账发现 REQUEST_TERMINAL 范围检查存在慢查询：`OR ... IN (scoped_orders)` 被优化器执行为相关子查询，对大量请求重复扫描约 2,630 条范围订单。EXPLAIN 显示 tf_request 全表扫描约 131,395 行，范围用户检查没有索引查找。

修正为去重 scoped_users 集合与 tf_request 连接，全量时补入所有用户，范围语义不变。新计划使用 uk_request 的 user_id 前缀读取请求，消除逐请求的范围订单扫描。该优化发生在采样结束后，不改变业务性能样本；完整回归与大样本重新对账验证结果正确。未修改表结构、原迁移或业务锁协议。

没有引入缓存、队列或放宽限购。当前结果是单次查询/交易性能基线与三轮争票正确性；尚无三轮性能置信区间、长时间稳态、独立部署或 V2 改造对比。下一阶段如进行 Redis/MQ 实验，应固定同样数据、负载和资源，再比较性能与正确性。

## 5. 批次6补充基线与观测（2026-10-06）

本轮保留阶段2的批次5最终包五分钟基线，新增带观测的本机短窗口阶梯筛查：20/50/100/200线程，每点10s预热、30s测量、一轮，查询与下单/支付分别运行。固定1000活动/3000场次/9000票档及合格用户，交易支付后退款以释放资格；退款是真实额外负载，不计入两接口样本。未重置测试库，没有云服务器。短筛查不作为计划中60+300s、三轮、云端等资源比较的替代。

结果、原始逐请求样本与P95/P99重算见[批次6报告](assets/04/20261006-batch6/summary.md)和[逐点表](assets/04/20261006-batch6/load-table.md)。首轮200线程四项查询P95约561～575ms超过500ms，已保留失败；下单905.007ms、支付925.918ms，零系统错误。不能以大量成功或零错误掩盖查询延迟未达标。

采集客户端成功/拒绝/异常、P95/P99，Hikari active/idle/pending/timeout/acquire与usage计时，JVM内存/GC/线程/CPU、应用与压测器进程CPU/RSS，MySQL服务级行锁等待累计与当前等待等。Micrometer计时为累计COUNT/TOTAL_TIME与滚动MAX，不是连接等待P95；客户端原始样本才用于接口分位数。只向日志采样，HTTP管理面仍仅health；默认关闭，启用TF_OBSERVABILITY_ENABLED=true，每5s采样。

数据库细粒度锁等待performance_schema读取被当前专用账号拒绝，未提权；server-wide计数不能当本项目独占指标。首轮Windows服务CPU读取缺失且只取一个mysqld进程，原始记录保留并明确无效，不解释为0%使用；采集工具修正为列出全部进程、不可读CPU记null，再复测。连接池排队是观察事实，不等于锁等待或SQL瓶颈已定位。加大连接池可能加重DB压力，本批不调整池大小。

正式目标在Redis/MQ优化前冻结：相应查询500ms、同步下单/支付1s、系统异常率<1%；异步以可靠受理和最终建单量、端到端P95/P99、30s终态与恢复100在途60s判断，售空/限购/限流独立计数。云端每负载点至少三轮，出现持续积压/错误/饱和停止增加负载并留失败；新增受理吞吐不等于建单吞吐。不预设倍数提升。
