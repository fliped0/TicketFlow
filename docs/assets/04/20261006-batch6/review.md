# 批次6关键设计复盘

先沿一条成功链路看：Lua只留下临时预占；MySQL提交请求/资格/发件箱后才返回202；RabbitMQ送的是工作通知；消费者在数据库里创建订单和结果后才ACK。客户端查到SUCCEEDED和orderId才知道建单完成。受理吞吐和建单吞吐分别计量，202不能冒充201。

再看失败链路：Lua预占后HTTP超时，此时DB可能已提交。直接加回票可能让另一人占走，而原消费者继续建单。因此先锁用户/原请求核实事实：已受理继续恢复，无行则提交REJECTED封口，之后才释放；迟到受理被封口挡住。

work_version解决旧工作者问题：租约到期后恢复者更新版本，旧工作者重新取得锁时版本不匹配，不能再提交。epoch解决旧世界问题：Redis重建为新代，旧释放和旧投影不能在新库存上再加票。两者都配合数据库事实，不能仅靠超时推断失败。

理解一次连接池等待：池最多20条连接，最终pending采样峰值180，说明当时有请求排队等连接；不是180个MySQL行锁，也不是180次超时。连接获取滚动MAX约2.412s、timeout累计0，可以同时成立。要确定根因，下一步需关联SQL持有时间、锁等待、CPU与负载器，不能直接把池调到200后宣称优化。

本批独立任务：用自己的话说明“客户端超时后，为什么既不能换一个请求键，也不能直接释放预占？”再根据baseline-summary.json找一个pending>0的观测窗口，区分“等连接”和“等数据库行锁”。当前没有performance_schema权限，所以可说“尚不能判断行锁”，不能补造结论。
