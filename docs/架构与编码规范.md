# TicketFlow 架构与编码规范

## 1. 决策与范围

2026-09-29 经用户确认，后端使用统一按技术职责分包的单体结构。controller、service、mapper、model 各建立一套，用户、活动、订单等业务类放入相应层。

总体设计中的 identity、catalog、inventory、order、payment、trade 是业务职责和数据归属，不再对应顶层 Java 包。保留单个 backend Maven 应用，Java 17、MySQL 8.0.45 及既有 HTTP 契约继续适用。

## 3. 调用与数据边界

1. Controller 处理 HTTP、请求对象和认证身份，调用 Service，返回 ApiResponse<VO>。不依赖 Mapper，不执行 SQL。
2. Service 校验业务规则、编排用例并控制事务，调用所属业务的 Mapper；跨业务交易由明确的交易服务协调。
3. Mapper 只负责参数绑定及数据库访问，返回实体或专用查询投影，不返回 HTTP 响应。
4. model/dto 表示输入，model/vo 表示对外结果，model/entity 表示持久化数据。实体包含的密码哈希等字段不得直接作为接口响应。
5. config 装配组件和执行受控初始化；security 实现认证授权适配。认证适配器可通过 Mapper 只读查询当前账号及角色，账号业务规则仍由 Service 负责。
6. common 放通用响应、异常映射和追踪，不引用具体业务 Service 或 Mapper。
7. 所有业务数据写入遵循详细设计的事务及锁协议。包结构本身不构成数据库一致性保证。

当前 Service 使用具体类；出现替换实现或需要稳定模块契约时再提取接口。Model 的 Java record 按职责放入独立文件，不嵌在 Controller 或 Service 内。

## 4. 本次修正

- 原 identity 包中的用户业务类移动至统一分层包。
- GET /api/v1/users/me 由 AuthController 调用 IdentityService.getCurrentUser，数据库访问归入 Service。
- 查询时重新检查账号是否存在及 enabled；如果认证后账号状态变化，返回 401，避免空指针或返回已禁用账号。
- JWT 的数据库身份转换移入 security，配置类负责装配。
- 请求、响应对象拆成独立 DTO / VO，响应 JSON 字段和接口路径保持兼容。
- 测试包同步移动，以 clean verify 检查组件扫描、MyBatis Mapper 注册和安全过滤链。

## 6. 开发交付要求

2026-10-01 批次 3 沿用统一分层，TradeController 调用 OrderApplicationService；TradeExecutor 用 TransactionTemplate 管理单个 READ COMMITTED 事务及保存点。交易、订单与库存 Mapper 使用 JdbcTemplate，与认证 Mapper 共用同一数据源和事务管理器；无独立连接、二级缓存或 REQUIRES_NEW。BusinessRejection 只用于可持久化的已知规则拒绝，数据库和系统异常退出整笔事务。DatabaseClock 在业务锁齐备后发出新的 UTC 取时 SQL。

每个功能批次同步维护代码、OpenAPI、测试结果和开发进度；通过测试后提交并推送 GitHub。结构调整如不改变 HTTP 契约，记录实现类映射，不修改接口版本。历史测试报告及源码哈希保持原样，新批次另存报告。

2026-10-03 批次 4 在现有层内扩展取消、支付、退款和关单。PaymentMapper 管理支付/退款记录，PaymentSimulator 仅执行本地无外部副作用的模拟；测试通过 bean 覆盖注入失败，不暴露公开成功参数。TradeExecutor.internal 为系统关单提供独立事务入口，锁当前订单所属用户但不要求 enabled，不写虚构客户端请求。OrderExpiryJob 仅编排扫描并调用应用服务，Controller 不调用关单入口。订单详情采用只读 REPEATABLE READ，以一致快照组合订单与交易记录。

批次 5 新增 AdminOrderController、AdminOrderService、AdminOrderMapper 及独立查询模型，管理员订单列表和统计在只读 REPEATABLE READ 事务中查询。Mapper 通过绑定参数构造可选筛选，管理列表以 JOIN 读取成功支付与退款，避免逐单查询。运维对账使用 scripts/reconcile.sql 的只读一致性快照；不提供修复入口。进程及网络故障注入全部在 scripts/batch5-experiments.py 中完成，生产 Java 代码不包含提交故障钩子。

## 7. 批次6观测与V2边界（2026-10-06）

本批实现config/OperationalMetricsSampler，以现有Micrometer注册表采样JVM、进程、Hikari及规范HTTP指标；TF_OBSERVABILITY_ENABLED默认false，只向日志输出白名单指标与标签，不新增管理HTTP接口、业务SQL或Redis/MQ依赖。scripts/batch6-baseline.py负责客户端原始延迟及只读数据库/OS观测，不能把采样缺失当零；细粒度锁权限缺失记为未获得。

V2具体类仍按统一controller/service/mapper/model分层，Redis/MQ连接与适配由config装配；监听器只调Service，事务内禁止网络调用。长期请求状态必须独立于原TradeExecutor，门禁前缀覆盖同步建单及ASYNC生命周期。拟新增职责与顺序见[协议第5节](03_V2异步抢票协议.md#5-锁顺序与代码职责)。未实现类不创建空壳，增量DDL不得放入运行Flyway目录提前生效。

## 8. 批次7缓存与限流

CatalogController仍只调用CatalogService；公开方法在CatalogCacheService.query额度内编排，缓存元数据的回源使用只读REPEATABLE READ短事务，RedisGateway的网络调用全部在事务外。管理查询走DB快照，交易Mapper/TradeExecutor不调用缓存。目录写入与audit、tf_catalog_revision递增在同一事务；按版本键逻辑失效，无需在锁内调用Redis或依赖提交后的不可靠DEL。代价是每次命中仍读一条版本SQL，任何目录变更使整个目录缓存切代；旧键靠TTL回收。

RedisFeatureConfiguration/Properties负责装配和受控参数，config/RedisGateway负责Redis字符串与Lua适配。PurchaseRateLimiter在OrderApplicationService.create开启TradeExecutor之前执行，先只读检查已有原键，真正重放/异参/库存判定仍由锁内交易执行器负责。没有修改现有用户→目录→资格→库存锁序。新增Flyway V2仅实现目录版本表，异步设计中的五表及mode尚未迁移。

## 9. 批次8实验分层

实验也沿用共享层：test目录的config/MqLabBroker与MqLabConfirmProxy适配AMQP/故障传输，model保存消息、发布结果及拓扑，mapper/MqLabMapper只执行SQL，service/MqLabService负责inbox/副作用/流水事务；RabbitMqLabIT编排测试，MqLabWorkerProcess是可强杀子进程入口。未增加Controller或空壳生产消费者。AMQP依赖为test scope，实验类、随机表DDL和故障钩子不进入可运行应用包。

发布、连接及ACK检查不处于DB事务中；MQ消费回调先调用Service，返回后才能ACK。数据库事务内的故障暂停仅在test子进程中，用于强杀验证，不是生产的网络调用。批次9仍须按门禁/用户/请求/目录/资格/库存顺序实现票务事务，不能把实验计数表去重当作生产订单锁协议已完成。


## 10. 批次 9：异步主流程

PurchaseRequestController 只调用 PurchaseRequestService/PurchaseModeService。AsyncRedisGateway 与 AsyncBrokerGateway 负责网络适配并拒绝在 DB 事务内调用；AsyncOrderService、AsyncLifecycleService、AsyncEvents 和 OutboxPublisher 编排业务；AsyncGateMapper/AsyncRequestMapper/OutboxMapper 使用现有 JdbcTemplate 和同一事务管理器。AMQP 客户端从实验 test scope 提升为运行依赖，实验类仍仅在 test 下。

AsyncTransactions 创建独立 READ COMMITTED、5 秒预算事务；结果查询使用只读 REPEATABLE READ，单进程独立查询额度在事务前检查。新建 SYNC/ASYNC 交易及生命周期以 gate S 为锁前缀，维护以 gate X 为前缀；再锁用户，异步请求/原幂等记录、目录、资格、库存与 queued_count 按协议顺序读取。生命周期在确认本人所有权后先锁对应异步请求，再锁订单/资格/库存，避免他人操作持有不相关请求锁。旧 TradeExecutor 的保存点及整笔回滚语义保留。

消费者短事务领取 PROCESSING 工作版本，另开业务事务重查版本/owner/租约，锁齐后重新读取 UTC。租约过期只能重试或等待扫描，业务截止才允许失败释放。DATETIME 通过 UTC 日期字符串读取，避免 JDBC Timestamp 使用 JVM 时区导致截止偏移。恢复事务提交 RETRY_WAIT 与下一 BROKER 发件箱后 ACK；恢复写失败停止通道，坏信封才进入死信。

Redis Lua 的类型校验先于库存写入，回执 complete 最后写入；部分/未知回执不猜测释放。投影按票档连续序号推进，重复序号不重补、缺号等候、关键键缺失暂停门禁。回补只删除原 token 拥有的资格。初始 READY 视图只能在开售前的配置入口建立，开售后重建/孤立预占封口留批次 10。不能把正常取消/退款投影已完成写成完整故障恢复已完成。

## 11. 批次 10：恢复与运维分层

AsyncRecoveryService 编排孤立封口及维护版本/epoch 重建，AsyncRecoveryMapper 负责快照查询与数据库不变量核对。门禁 X 提交暂停后才执行 Redis 网络操作；新 epoch、有效请求工作版本和替代 BROKER 事件共同提交。所有新建、消费、生命周期及配置仍使用同一门禁前缀，不引入跨数据库连接的事务。

AsyncReconciliationService 使用只读快照与重复在线观测；AsyncDeadReplayService 将重放回执与替代事件同事务提交后才允许 ACK。AsyncAlerts 记录日志、有限标签指标及数据库告警收件箱；AsyncOperationsService 经本地 async-ops.ps1 调用，不暴露新的 HTTP 管理路由。Flyway V4 只增加告警/重放回执表，历史迁移不修改。

测试专用 AsyncCrashWorker 和 AsyncMysqlCommitProxy 在 test 目录中定位强杀及真实 COMMIT 传输故障；不进入应用 jar。新运维入口运行时关闭后台扫描，使用现有专用环境凭据及回环随机 HTTP 端口，操作完成关闭应用。
