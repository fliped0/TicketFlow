## 1. 目的与范围

本文描述系统应提供的能力、业务约束及验收条件，为总体设计、详细设计和测试提供依据。Java 后端为开发主线，高并发治理和 Agent 在后续迭代加入。

阶段 0 已确定的方向作为本阶段输入。依据用户“需求分析已完成”并继续总体设计的指示，本文件业务范围及规则作为 v1.0 需求基线；性能与恢复数值仍为待环境验证的目标。本文不确定数据库表结构、具体接口路径和中间件实现方式。

### 1.1 版本范围

| 迭代 | 范围 | 完成边界 |
| --- | --- | --- |
| V1 基础业务 | 用户、活动、场次、票档、库存、订单、模拟支付、取消、简化退款、管理查询 | 核心链路和并发正确性通过验收 |
| V2 高并发改造 | 热点缓存、限流、异步下单、故障恢复与性能对比 | 在固定环境中完成正确性和性能验证 |
| V3 Agent 扩展 | 活动查询、个人订单查询、规则问答和受控操作 | 工具权限、业务正确性和问答质量通过验收 |

V1 内部可分模块交付，但完成 V1 时仍须覆盖简化退款。真实支付、实名核验、选座、短信、第三方票务、微服务和 Kubernetes 不在 V1 范围内。前端框架与页面美化不作为后端验收前提，可通过接口测试和简单演示界面完成验收。

### 1.2 优先级

- P0：V1 必须完成，缺少该能力会破坏核心业务或数据正确性。
- P1：V1 必须完成的辅助能力，可在核心链路之后交付。
- P2：V2 或 V3 的扩展能力，不阻塞 V1 验收。

## 2. 术语与角色

### 2.1 业务术语

| 术语 | 含义 |
| --- | --- |
| 活动 | 演唱会、展览或赛事等对外展示的业务对象 |
| 场次 | 某活动在指定时间、地点的一次举办安排 |
| 票档 | 某场次下的一类价格与库存，如普通票、VIP 票，不包含具体座位 |
| 可售库存 | 当前可用于新订单的票数 |
| 占用库存 | 待支付订单或已受理下单请求暂时预留的票数 |
| 已售库存 | 已支付且尚未成功退款的票数 |
| 幂等 | 同一个业务请求重复执行时，不重复创建订单、支付或释放库存 |
| 受理成功 | 系统接收了抢票请求，异步处理时不等于订单创建成功 |

### 2.2 角色与权限

| 能力 | 游客 | 普通用户 | 管理员 |
| --- | --- | --- | --- |
| 查询上架活动、场次和票档 | 允许 | 允许 | 允许 |
| 注册与登录 | 允许 | 允许 | 允许 |
| 下单、支付、取消、退款 | 需登录 | 仅操作本人订单 | 不代用户操作 |
| 查询个人订单 | 禁止 | 仅本人 | 仅本人 |
| 维护活动、场次和票档 | 禁止 | 禁止 | 允许 |
| 查看全部订单与基础统计 | 禁止 | 禁止 | 允许 |

游客是未认证访问状态，不新增持久化角色。管理员账号由受控初始化流程创建，公开注册不能授予管理员权限。后台查询权限不自动包含代付、代退或修改订单状态的权限。

## 3. 功能需求

每项需求编号保持稳定，后续设计与测试通过编号引用。表中的验收条件为需求层面的结果要求，详细测试步骤在阶段 04 补齐。

### 3.1 用户与认证

| 编号 | 优先级 | 需求 | 验收条件 |
| --- | --- | --- | --- |
| FR-USER-001 | P0 | 用户以账号和密码注册 | 合法且未占用账号可注册；重复账号和非法参数被拒绝；注册结果不含密码信息 |
| FR-USER-002 | P0 | 用户登录并获得访问凭证 | 正确凭据登录成功；错误凭据被拒绝；过期、缺失或被篡改的凭证不能访问受保护能力 |
| FR-USER-003 | P0 | 获取当前用户基本信息 | 仅返回允许公开给本人的字段；不接受客户端指定身份来替代认证身份 |
| FR-USER-004 | P0 | 区分用户与管理员权限 | 普通用户无法调用管理功能；修改请求中的角色字段无法提权 |

### 3.2 活动、场次与票档查询

| 编号 | 优先级 | 需求 | 验收条件 |
| --- | --- | --- | --- |
| FR-EVENT-001 | P0 | 分页浏览活动，按名称关键词、城市和活动类别筛选 | 只返回上架活动；组合筛选有效；排序稳定；无结果返回空集合 |
| FR-EVENT-002 | P0 | 查看活动详情 | 返回名称、介绍、城市、地点与场次；草稿和下架活动不向公众展示 |
| FR-SESSION-001 | P0 | 查询场次信息 | 返回举办时间、售票起止时间和销售状态；场次与活动归属一致 |
| FR-TIER-001 | P0 | 查询票档信息 | 返回票档名称、价格和可售状态；展示库存不构成下单成功承诺 |

### 3.3 订单与库存

| 编号 | 优先级 | 需求 | 验收条件 |
| --- | --- | --- | --- |
| FR-ORDER-001 | P0 | 登录用户选择票档并提交订单 | 满足销售窗口、限购与库存条件时创建待支付订单；服务端计算金额和期限；失败不残留无主占用 |
| FR-ORDER-002 | P0 | 重试同一下单请求 | 相同用户、相同幂等键和参数返回同一业务结果；同键不同参数被拒绝 |
| FR-ORDER-003 | P0 | 查询本人订单列表和详情 | 可按状态分页；含票档快照、数量、金额、状态和期限；不能读取他人订单 |
| FR-ORDER-004 | P0 | 取消待支付订单 | 取消后订单不可支付；库存和限购资格只释放一次；重复取消不重复释放 |
| FR-ORDER-005 | P0 | 自动关闭超时待支付订单 | 到期后拒绝支付；超时关闭后释放占用；重复调度或服务重启不重复处理 |
| FR-STOCK-001 | P0 | 并发下单保持库存正确 | 不超卖、库存不为负；同场次限购在并发下仍有效；失败可追踪和恢复 |
| FR-ORDER-006 | P2 | 异步抢票结果查询 | V2 返回请求编号与处理中状态；用户可查询成功或失败；成功结果关联唯一订单 |

### 3.4 模拟支付与简化退款

| 编号 | 优先级 | 需求 | 验收条件 |
| --- | --- | --- | --- |
| FR-PAY-001 | P0 | 对本人待支付订单执行模拟支付 | 仅在有效期内成功；金额取自订单；不接入真实资金；支付成功记录与订单一致 |
| FR-PAY-002 | P0 | 重复支付与失败处理 | 重试返回已有结果；同一订单最多一笔成功支付；模拟失败保持待支付直到取消或超时 |
| FR-REFUND-001 | P0 | 对符合条件的本人已支付订单申请全额模拟退款 | 成功后变为已退款；不支持部分退款；重复申请不重复退款或释放库存 |
| FR-REFUND-002 | P1 | 查看退款规则与结果 | 下单前能查看规则；订单保留成交时的规则快照；不符合规则时返回明确原因 |

### 3.5 管理能力

| 编号 | 优先级 | 需求 | 验收条件 |
| --- | --- | --- | --- |
| FR-ADMIN-001 | P0 | 创建和修改活动草稿、上下架活动 | 缺少必填信息或有效场次、票档时不能上架；下架停止新购票，不隐式取消已有订单 |
| FR-ADMIN-002 | P0 | 配置场次和票档 | 校验时间关系、正数价格、非负整数库存及归属关系；不能关联不存在的活动或场次 |
| FR-ADMIN-003 | P0 | 管理库存与售卖信息 | V1 仅首次开售前可修改价格、容量和关键时间；开售后禁止直接覆盖库存；保留修改记录 |
| FR-ADMIN-004 | P1 | 查询订单和统计数据 | 可按订单号、场次、状态和创建时间筛选；提供订单数、成功支付总额、成功退款总额及二者差额；统计口径标明时间范围 |

## 4. 核心业务规则

### 4.1 基线业务参数

以下为第一版采用的业务规则。后续调整需记录需求变更，并同步修改用例、状态约束和测试数据。

| 编号 | 事项 | 基线值或规则 | 理由 |
| --- | --- | --- | --- |
| BR-001 | 单次购买数量 | 每单一个票档、一张票 | 先完整验证库存与订单一致性 |
| BR-002 | 场次限购 | 每用户同场次最多一个有效订单；有效指待支付或已支付，V2 还包含处理中请求 | 防止换票档绕过限制；取消或退款成功后可重新购买 |
| BR-003 | 支付期限 | 创建订单后 15 分钟，且不晚于场次开始时间，取较早者 | 及时归还未支付库存；实际期限返回给用户 |
| BR-004 | 退款范围 | 场次开始前可全额模拟退款，不收手续费；开始时刻及之后不可退 | 建立最小退款闭环；规则仅用于本项目模拟 |
| BR-005 | 退款库存 | 退款成功后归还可售库存；是否可新下单仍受上下架和销售窗口约束 | 库存归还不等于重新开放销售 |
| BR-006 | 票务凭证 | V1 以已支付订单作为购票凭证 | 暂不设计独立出票、二维码核销和入场系统 |
| BR-007 | 上架后变更 | 首次开售后冻结场次时间、价格、容量与退款规则；仍允许修改非关键展示文案和上下架 | 避免存量订单规则被覆盖 |
| BR-008 | 用户输入边界 | 账号 4—32 位字母、数字或下划线；密码 8—64 字符；列表每页默认 20、最大 100 | 提供可测试的输入边界，后续可配置 |

### 4.2 售票与时间

所有业务判断使用服务端时间，展示默认采用 Asia/Shanghai。售票开始时间必须早于售票结束时间，售票结束时间不得晚于场次开始时间。

允许下单的时间区间为“售票开始时间 ≤ 当前时间 < 售票结束时间”，并要求活动上架、票档有效、场次未开始。支付要求“当前时间 < 订单支付期限”。到达支付期限的时刻即不可支付，即使超时关闭任务尚未运行也必须拒绝。

活动下架只阻止新订单；下架前已创建订单可继续在有效期内支付，也可按原规则取消或退款。整场取消和强制批量退款暂不包含在 V1 中。

### 4.3 金额与历史快照

所有金额以人民币计，精确到分。服务端按有效票价和购买数量计算订单金额，不信任客户端价格。V1 不包含优惠券、折扣和服务费。

订单需保留成交时的活动名称、场次时间、地点、票档、单价、数量、金额和退款规则快照；后台文案变动不能改变历史订单事实。已经被订单引用的活动、场次和票档不可物理删除。

### 4.4 库存守恒

在固定票档容量、无在途转换的稳定状态下：

```text
票档总容量 = 可售库存 + 占用库存 + 已售库存
```

创建待支付订单将可售转为占用；支付将占用转为已售；取消或超时将占用转回可售；退款成功将已售转回可售。每次转移只能生效一次。

V2 中在途请求也必须有可追踪的占用记录。短暂跨组件差异必须能够核对并收敛，不能通过清空缓存或随意增加库存掩盖问题。

### 4.5 状态与竞争处理

| 原状态 | 动作与条件 | 目标状态 | 库存结果 |
| --- | --- | --- | --- |
| 无订单 | 通过下单校验并占用成功 | 待支付 | 可售转占用 |
| 待支付 | 期限内支付成功 | 已支付 | 占用转已售 |
| 待支付 | 用户取消 | 已取消 | 占用转可售 |
| 待支付 | 达到支付期限 | 已关闭 | 占用转可售 |
| 已支付 | 符合退款规则且退款成功 | 已退款 | 已售转可售 |

已取消、已关闭和已退款为该订单的终态，重新购买需创建新订单。支付与取消、支付与超时关闭发生竞争时，只能有一个状态变更成功；失败的一方返回最终状态，不得出现“支付成功但库存已释放”。

V1 模拟支付、退款以同步结果为准，失败不改变原业务状态。如未来引入外部支付或异步退款，应单独评审处理中、失败补偿等状态，不能直接套用当前模型。

## 5. 用例与业务流程

### 5.1 UC-001：管理员发布活动

参与者：管理员。前置条件：已认证并具备管理权限。

1. 创建活动草稿，填写名称、介绍、类别、城市和地点。
2. 配置场次时间及售票窗口。
3. 配置票档名称、价格和容量。
4. 发布活动，系统校验必填信息和关联对象。
5. 发布成功后，游客可查询活动；是否可购买取决于销售窗口。

异常：缺少票档、时间冲突或非法库存时拒绝发布并返回原因；原草稿保留。关联需求：FR-ADMIN-001、FR-ADMIN-002、FR-EVENT-001。

### 5.2 UC-002：用户购买并支付

参与者：普通用户。前置条件：活动可售，用户已登录，具有购买资格。

1. 用户查询活动、场次和票档并阅读退款规则。
2. 提交票档和唯一请求标识。
3. 系统校验身份、销售窗口、限购及库存，创建待支付订单。
4. 返回订单号、金额、支付期限。
5. 用户在期限内模拟支付。
6. 系统记录支付结果，订单成为已支付，用户可查询凭证。

异常：库存不足、未开售、已停售、限购或身份失效时拒绝下单。响应丢失时用户以原请求标识重试，不创建第二笔订单。支付失败时可在期限内重试。关联需求：FR-ORDER-001、FR-ORDER-002、FR-STOCK-001、FR-PAY-001、FR-PAY-002。

### 5.3 UC-003：取消与超时关闭

参与者：普通用户或系统超时任务。前置条件：订单待支付。

1. 用户主动取消，或系统发现订单已到期。
2. 系统校验当前状态，完成一次状态迁移。
3. 释放库存和对应限购资格，保留订单及取消或关闭原因。
4. 重复请求返回已有结果，不重复释放。

异常：订单已支付时拒绝取消或关闭；可按规则走退款。超时任务停机后恢复时应处理漏掉的到期订单。关联需求：FR-ORDER-004、FR-ORDER-005、FR-STOCK-001。

### 5.4 UC-004：申请退款

参与者：普通用户。前置条件：本人已支付订单且未到场次开始时间。

1. 用户查看订单退款规则并提交退款申请。
2. 系统校验归属、状态和退款时限。
3. 完成全额模拟退款，记录退款结果。
4. 订单变为已退款，归还库存并释放限购资格。

异常：他人订单、未支付订单和已过退款时限的申请被拒绝。模拟退款失败时仍为已支付，库存不归还；用户可在时限内重试。关联需求：FR-REFUND-001、FR-REFUND-002、FR-STOCK-001。

### 5.5 UC-005：异步抢票扩展

V2 才引入：提交请求后可能得到“处理中”，系统返回可查询的请求编号；用户查询后获得订单创建成功或明确失败。请求受理、库存占用、创建订单和失败补偿必须可追踪。暂时无法确定结果时保持处理中，不能先宣告失败再悄悄生成有效订单。

## 6. 非功能需求

### 6.1 安全、正确性与可维护性

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| NFR-SEC-001 | 密码使用带盐单向密码哈希保存；凭证、密码不写入日志和返回数据 | 检查存储样本、响应和日志；账号认证测试 |
| NFR-SEC-002 | 服务端认证、角色校验和订单归属校验同时生效 | 未登录、过期凭证、越权访问、伪造用户标识测试全部拒绝 |
| NFR-SEC-003 | 外部访问使用 HTTPS；密钥由环境配置注入 | 部署检查；仓库和日志中无真实密钥；本地回环开发可使用 HTTP |
| NFR-DATA-001 | 订单、库存、支付和退款满足第 4 章规则 | 并发及故障恢复后检查守恒、唯一性和状态合法性，违规数量为零 |
| NFR-REL-001 | 重试、重复调度和进程重启不造成重复副作用 | 对下单、支付、退款和关单执行重复与中断测试 |
| NFR-OBS-001 | 核心请求可通过请求编号关联订单和处理结果 | 从一次失败请求定位对应记录；日志区分业务拒绝和系统异常 |
| NFR-API-001 | 响应包含稳定业务结果码，错误可读且不泄露内部细节 | 参数非法、库存不足、限流和内部错误可区分；不返回堆栈或数据库细节 |
| NFR-MAINT-001 | 环境可复现，需求与测试可追踪 | 按部署文档可启动指定版本；每个 P0 需求至少有成功、失败或边界测试 |

### 6.2 性能与恢复目标草案

以下数值是拟议验收目标，不是已测结果或生产服务承诺。机器配置尚未确定，阶段 06 必须先固定 CPU、内存、存储、组件版本、资源限制、数据量和压测方式，再确认数值基线。

| 编号 | 场景 | 建议目标与测量口径 |
| --- | --- | --- |
| NFR-PERF-001 | V1 活动列表和详情 | 1,000 个活动、每活动 3 场次、每场次 3 票档；20 并发用户，预热 1 分钟、测量 5 分钟；P95 ≤ 500 ms，系统异常率 < 1% |
| NFR-PERF-002 | V1 下单与支付接口 | 库存充足且用户满足限购；20 并发用户，预热 1 分钟、测量 5 分钟；各接口 P95 ≤ 1 s，系统异常率 < 1% |
| NFR-PERF-003 | 库存竞争正确性 | 1,000 个不同用户通过 100 并发工作线程争抢 100 张票；10 秒内发起全部请求；无取消、退款和超时影响；最终 100 个有效订单、库存为零、无超卖与重复有效订单 |
| NFR-PERF-004 | V2 优化比较 | 使用相同环境、数据和负载重复至少 3 轮；记录吞吐量、P95/P99、系统异常率和资源占用；达到改造前约定目标且不降低正确性 |
| NFR-REL-002 | V1 超时回收 | 服务正常时，订单到期后 60 秒内完成关闭与释放；停机恢复后 60 秒内完成测试集中 100 个漏处理订单的回收 |
| NFR-REL-003 | V2 异步恢复 | 测试集中 100 个在途请求在依赖恢复后 60 秒内得到可查询的终态；无法收敛的请求产生可定位告警 |

系统异常率以服务内部错误、意外超时为分子，以全部请求为分母；预期的售罄、限购和限流单列统计，不混入系统异常率。性能报告必须同时展示成功业务量，防止以快速拒绝大量请求冒充吞吐提升。

NFR-PERF-003 进行至少 3 次独立重置实验。若启用限流导致请求被拒绝，需在不突破限购规则的前提下重试至结果收敛，并独立记录拒绝数；该场景验证正确性，不声称“1,000 并发”或特定 QPS。

## 7. 数据与外部依赖边界

### 7.1 逻辑数据对象

系统需保存用户、活动、场次、票档、库存、订单、模拟支付记录、模拟退款记录和关键管理操作记录。一个活动包含多个场次，一个场次包含多个票档；V1 一个订单属于一个用户并购买一个票档的一张票。

订单及其支付、退款记录必须可关联追踪。数据保留期限和备份实现由部署阶段补充；V1 不实现用户自助注销和历史订单清理。逻辑对象不等于必须建立同名数据库表，具体结构在详细设计中确定。

### 7.2 外部依赖

V1 不依赖真实支付渠道、短信平台或第三方票务数据，使用可重复的测试数据和模拟交易。核心 Java 业务必须可在 Agent 不可用时独立运行。Redis、MQ 和模型服务故障后的具体降级、补偿方案在设计阶段给出。
