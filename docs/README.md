# TicketFlow 软件工程文档

本目录用于集中维护 TicketFlow 项目在立项、需求、设计、测试、部署、性能优化、Agent 扩展和项目总结等阶段产生的正式文档。

## 1. 文档产出原则

TicketFlow 采用“软件工程开发流程 + 迭代式开发”。每个阶段均按照以下闭环推进：

```text
讨论阶段内容
    ↓
形成设计决策
    ↓
输出或更新阶段文档
    ↓
依据文档开发与测试
    ↓
按验收标准确认结果
    ↓
回写实际实现与变更
    ↓
进入下一阶段
```

文档必须反映项目的实际决策与实现，不为了罗列技术而提前引入不必要的复杂度。开发过程中若需求、架构或实现发生变化，应同步更新对应文档，并在修订记录中说明原因。

## 3. 统一编写规范

### 3.1 文件命名

- 阶段文档使用两位数字作为前缀，格式为 `NN_文档名称.md`。
- 同一主题原则上只保留一份主文档，通过修订记录持续更新。
- 图表和附件后续统一放入 `assets/`，并按阶段建立子目录，例如 `assets/02/`。

### 3.2 标题层级

- 一级标题：文档全名，每份文档仅一个。
- 二级标题：`## 1. 章节名称`。
- 三级标题：`### 1.1 小节名称`。
- 四级标题：`#### 1.1.1 条目名称`，仅在确有必要时使用。
- 不跳级使用标题，正文列表不使用标题替代。

### 3.3 文档状态

每份正式文档在开头维护以下信息：

| 字段 | 说明 |
| --- | --- |
| 文档状态 | 草稿 / 评审中 / 已基线 / 已废止 |
| 当前版本 | 使用 `v主版本.次版本`，例如 `v1.0` |
| 创建日期 | 首次建立文档的日期 |
| 最近更新 | 最近一次有效修改日期 |
| 适用阶段 | 文档对应的软件工程阶段 |

状态含义：

- **草稿**：内容仍在讨论，不能作为开发验收的唯一依据。
- **评审中**：主体内容完成，正在确认关键决策。
- **已基线**：当前迭代采用的正式版本，开发和测试应与其保持一致。
- **已废止**：已被其他文档替代，仅作历史参考。

### 3.4 需求与设计追踪

从需求分析阶段起，为可追踪条目分配稳定编号：

- 功能需求：`FR-模块-序号`，例如 `FR-ORDER-001`。
- 非功能需求：`NFR-类别-序号`，例如 `NFR-PERF-001`。
- 接口：`API-模块-序号`。
- 测试用例：`TC-模块-序号`。
- 风险：`RISK-序号`。
- 业务规则：`BR-序号`；用例：`UC-序号`。
- 架构决策：`ADR-序号`，用于记录方案、取舍及重新评估条件。

后续设计、接口、代码提交说明和测试用例应引用对应编号，保证需求可以追踪到实现和验证结果。

## 4. 变更管理

每份文档末尾保留修订记录。影响业务边界、数据结构、接口契约、性能目标或安全策略的变更，应至少写明：

1. 变更内容；
2. 变更原因；
3. 受影响模块；
4. 对开发、测试和部署的影响；
5. 对应版本与日期。

小范围措辞修正可以合并记录，不必为每个错别字单独增加版本。

## 5. 阶段完成标准

一个阶段只有在以下条件同时满足时才视为完成：

1. 阶段范围内的关键问题已经讨论并形成明确结论；
2. 对应 Markdown 文档已完成并通过检查；
3. 文档中的验收标准已满足，或未完成项已明确记录；
4. 实际实现与文档一致；
5. 已识别的变更已回写，遗留事项已进入后续计划。
