# TicketFlow：简历项目亮点与面试问题

2026-10-15，面向 Java 后端 / Agent 研发实习。内容依据当前源码与仓库内测试证据，不能据此宣称真实售票运营、生产高可用或已经达到商业容量。

## 1. 交易幂等与库存、订单一致性

**业务问题：** 用户重复点击、响应丢失重试，以及多人争抢最后一张票，不能多建单或多扣库存；系统异常不能留下半笔交易。

**实现：** `TradeExecutor.executeInSession` 自主管理 READ COMMITTED 事务，按 gate → 用户 → 请求 → 目录/资格 → 库存的顺序取锁。`(user_id,operation,request_key)` 唯一键和参数摘要区分原请求重放与异参冲突。业务拒绝回滚到保存点后保存拒绝结果，系统异常整笔回滚；成功回执在 commit 后返回。`InventoryMapper.reserve` 的条件更新、受影响行数校验与数据库库存守恒 CHECK 共同保护库存，不仅依赖 Redis。

**关键代码：** [TradeExecutor](../backend/src/main/java/com/ticketflow/service/TradeExecutor.java)、[OrderApplicationService](../backend/src/main/java/com/ticketflow/service/OrderApplicationService.java)、[InventoryMapper](../backend/src/main/java/com/ticketflow/mapper/InventoryMapper.java)、[V1 约束](../backend/src/main/resources/db/migration/V1__init_schema.sql)。

**证据：** `OrderIntegrationIT` 验证 20 个同键并发、跨票档限购、最后一张票、每个写入阶段回滚及锁后截止检查；[历史争票记录](06_性能测试与优化.md)为 1,000 用户、100 工作线程争抢 100 张票，三轮均 100 成功、900 售罄。不是“1,000 并发”。

**追问：** 为什么唯一键不能代替全部业务锁？为什么业务拒绝需要保存点？事务提交成功但响应丢失怎么办？为什么只重试明确的死锁/锁等待失败，而不盲目重试未知提交？锁用户行会造成什么吞吐取舍？

## 2. Redis 预占、可靠受理与异步建单

**业务问题：** 排队受理不能冒充订单成功，Redis 已预占但 MySQL 未提交时不能盲目释放；两个同场资格表也不能各自唯一却合起来超限。

**实现：** Lua 执行同场次预占、原键去重与限流；MySQL 提交受理请求、在途资格、queued_count 和 Outbox 后才返回 202。消费者再次锁内检查销售期限、资格和库存，并在同一事务完成 `B−1、available−1、reserved+1`、订单、结果与投影事件。数据库是权威，Redis 是可重建视图，保持 `capacity=available+reserved+sold`、`0≤queued_count≤available`。

**关键代码：** [PurchaseRequestService](../backend/src/main/java/com/ticketflow/service/PurchaseRequestService.java)、[AsyncRedisGateway](../backend/src/main/java/com/ticketflow/config/AsyncRedisGateway.java)、[AsyncOrderService](../backend/src/main/java/com/ticketflow/service/AsyncOrderService.java)。

**证据：** `AsyncPurchaseIT.reliable202ContainsFourDurableFactsBeforeBrokerPublication`、`sixBuyersCompeteForTheLastTicketWithoutOverselling`、`crossSessionSameKeyReleasesOnlyTheLosingCandidate`；[网页异步验收](assets/04/20261014-frontend-async/summary.md)包含两名用户末票竞争及回执丢失恢复。

**追问：** 为什么 202 仍需要 MySQL 事务？Lua 原子执行是否等于出错自动回滚？Redis free 与数据库 available 为什么可能不同？为什么同键跨场次仍需要数据库唯一约束？Redis 故障为什么不能直接用 available 初始化后继续放票？

## 3. 消息重投与故障恢复

**业务问题：** MQ publish 成功但 confirm 丢失、消费 commit 后 ACK 丢失、工作者崩溃、Redis 数据丢失，都可能产生重复或悬挂工作。

**实现：** 事务 Outbox、mandatory + publisher confirm、持久 quorum 队列、业务提交后 ACK；订单业务以请求行终态、唯一订单和工作版本去重。8 秒工作租约、5 秒事务预算、最多 30 秒业务截止分别处理不同问题；恢复时用门禁、维护所有权和 epoch 隔离旧工作。孤立预占先写持久拒绝栅栏再释放，投影序号保证重复释放不多补库存。

这不是端到端 exactly-once 消息投递：允许至少一次投递，由事务与幂等约束实现业务效果去重。MQ 实验的合成 inbox 与正式票务请求状态机是两套实现，不应混讲。

**关键代码：** [OutboxPublisher](../backend/src/main/java/com/ticketflow/service/OutboxPublisher.java)、[AsyncBrokerGateway](../backend/src/main/java/com/ticketflow/config/AsyncBrokerGateway.java)、[AsyncRecoveryService](../backend/src/main/java/com/ticketflow/service/AsyncRecoveryService.java)、[AsyncDeadReplayService](../backend/src/main/java/com/ticketflow/service/AsyncDeadReplayService.java)。

**证据：** [批次 10](assets/04/20261008-batch10/summary.md)包含 10 个子进程强杀窗口和真实 COMMIT 传输故障；100 在途请求一次恢复观测为 41.452 秒、60 成功/40 拒绝，包含原截止超时，不是 100 单全部成交，也不是吞吐 QPS。本次审查额外检查持续失败记录对后台扫描公平性的影响，修复见[问题记录](问题修复记录.md)。

**追问：** confirm 和 ACK 各证明什么？为什么不能先 ACK 再提交？工作租约与业务截止的区别？为什么重建不能延长原截止？旧工作者恢复后为什么不能提交？如何确保故障请求不一直挡住后面的正常请求？

## 4. 订单生命周期与可追溯验证

**业务问题：** 支付和关单竞争、退款重复调用及开场边界可能造成错误状态或重复库存回补。

**实现：** 状态机与时间条件在锁内重读数据库时钟；支付/退款唯一记录和库存流水与订单同事务提交。到期扫描分页、有时间预算和防重入；取消/退款仅处理本人订单，重复操作返回原编号。

**关键代码：** [OrderApplicationService](../backend/src/main/java/com/ticketflow/service/OrderApplicationService.java)、[OrderPolicy](../backend/src/main/java/com/ticketflow/service/OrderPolicy.java)、[OrderExpiryJob](../backend/src/main/java/com/ticketflow/service/OrderExpiryJob.java)、[只读对账 SQL](../scripts/reconcile.sql)。

**证据：** `OrderLifecycleIT` 用并发和锁等待构造支付/取消、支付/关单双向竞争，检查实际状态、库存、资格及流水；网页测试覆盖模拟支付、取消退款和原键恢复。

**追问：** 为什么请求到达时间不能作为付款截止判据？查询 PENDING 后再执行是否安全？为什么退款后仍保留原建单成功结果？模拟支付在事务内可行，真实支付是否也能这么做？

## 5. Agent 的工具权限与独立交易确认

**业务问题：** 模型输出不可信，不能靠提示词保证它不越权执行取消或退款，也不能把超时误认为未执行。

**实现：** Pydantic 严格参数和工具白名单固定调用路径；身份来自 Java JWT 当前账号，工具不接受任意 userId。模型只查询或准备确认卡；执行是独立入口，必须显式 approved，核对本人订单与快照。SQLite 持久保存确认、原幂等键与执行租约，未知结果用原键恢复。Java 业务数据由本地卡片呈现，不回传模型；规则资料来源哈希不符时停止规则回答。

**关键代码：** [tools.py](../agent/ticketflow_agent/tools.py)、[service.py](../agent/ticketflow_agent/service.py)、[confirmations.py](../agent/ticketflow_agent/confirmations.py)、[java.py](../agent/ticketflow_agent/java.py)、[gateway.py](../agent/ticketflow_agent/gateway.py)、[rules.py](../agent/ticketflow_agent/rules.py)。

**证据：** `test_confirmations.py` 覆盖伪造确认、跨用户、快照变化、响应丢失、租约和旧响应隔离；`test_rules.py`、冻结评估集及[历史模型路由评估](assets/04/20261011-agent-route/summary.md)有独立记录。确定性测试通过率不代表模型理解准确率；历史 60/60 仅指该冻结集合和当时模型配置。

**追问：** 提示词与服务端权限的区别？“帮我退款”和“我能退款吗”如何区分？执行超时为什么存 UNKNOWN？确认记录丢失怎么办？为什么普通聊天里的“确认”不能直接执行？当前是受限工具路由与审核资料检索，不应包装成任意多步自主 Agent 或向量 RAG 平台。

## 性能口径

| 类别 | 可引用证据 | 不可推导结论 |
| --- | --- | --- |
| 历史 V1 同步下单 | Windows 本机应用/MySQL/负载器，20 工作线程，60 秒预热 + 300 秒采样；下单 147.683 请求/秒、P95 70.906ms，支付和退款循环提供额外负载 | 不能称为最新异步版本性能、纯抢票峰值或云端 SLA |
| 历史同步争票正确性 | 1,000 用户、100 工作线程、100 票，三轮各 100 成功/900 售罄 | 不能称为千并发，也不能从售空拒绝速率推导成功订单吞吐 |
| ASYNC 可靠受理 | 202 必须已有持久受理四项事实，已有功能/故障测试 | 本次无同条件受理 QPS/P95/P99 压测，不填估算值 |
| ASYNC 最终建单 | 订单成功量、拒绝量和受理到终态时延应单独采样；已有 100 在途恢复实验 | 恢复收敛时间不是建单吞吐；不能写 Redis/MQ 带来若干倍性能提升 |

原始性能范围见[性能文档](06_性能测试与优化.md)与[阶梯表](assets/04/20261006-batch6/load-table.md)。200 线程查询 P95 超过既定 500ms 的失败保留，不能用零系统错误掩盖。

## 简历可用描述

**TicketFlow 模拟票务系统｜Java 17、Spring Boot、MySQL、Redis、RabbitMQ、Vue、Python/FastAPI**

- 实现选票下单、模拟支付、取消退款及异步抢票闭环，通过数据库事务、幂等请求与库存条件更新处理重复提交和并发竞争。
- 设计 Redis Lua 预占与 MySQL 持久受理流程，结合事务 Outbox、消费幂等、工作租约及 epoch 重建处理消息重投和状态恢复。
- 构建库存、资格、订单与交易流水对账，编写末票竞争、COMMIT 断连、子进程强杀及超时恢复测试，验证关键一致性场景。
- 接入受限 Agent 工具路由，以本人权限校验、独立确认和持久原键恢复保护取消/模拟退款操作。

投 Java 后端可选前四项技术亮点中的三项；投 Agent 研发再突出第五项。数字不是必填，只有能准确讲清实验条件时才加入。代码与证据达到展示门槛不代表求职者已经掌握实现；需要能独立画出一次请求的锁序、失败路径并现场修改/调试。
