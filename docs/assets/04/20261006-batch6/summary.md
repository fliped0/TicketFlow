## 3. 观测事实与缺口

最终Hikari active采样峰值20，pending峰值180，获取连接滚动MAX峰值2.4120889s，timeout计数0。MAX来自Micrometer计时器、不是连接等待P95；14/60测试方法数也不是性能样本数。线程提高时吞吐未同比增长，存在池等待，仍不能判断究竟是SQL、CPU、连接持有、同机负载器或锁造成。没有据此声称“数据库已成为瓶颈”或“Redis将提升数倍”。

进程/数据库观测及定时应用快照的精确计数见baseline-summary.json，涵盖JVM内存/GC/线程、应用/压测器CPU/RSS、连接池、HTTP累积计时及MySQL全局InnoDB锁计数。最终应用采样CPU峰值为整机35.073%，压测器15.612%；不是单核CPU占用或容器配额。服务级行锁等待计数不是本项目独占。

细粒度performance_schema.data_lock_waits读取被tf_test拒绝，未扩权。Windows服务CPU读取为空，首轮采集误把它写0且只选到一个mysqld辅助进程；该项**无效**，不能解释为数据库零CPU/只有11MB内存。工具修正后列出两个进程，CPU仍明确null；最终较大mysqld进程RSS采样峰值385,466,368字节。原始错误记录保留并注明；未将这些缺失替换成虚构数据。云端需要受控系统指标及只读性能表权限。

## 4. V2设计与检查口径

交付[异步协议](../../../03_V2异步抢票协议.md)、[接口草案](../../../api/v2-draft.md)、[数据库增量草案](../../../assets/03/v2/async-schema-draft.sql)，以及需求/总体设计/架构/测试/部署/性能增量。包含状态机、3个拟接口、5张表与场次模式字段、共同锁序、Lua预占、DB可靠受理、发件箱、幂等消费、有序投影、孤立封口、工作版本、epoch重建及六个故障时序窗口。

关键评审修正：无预占的Lua业务拒绝持久原键结果但不写释放事件；有预占的拒绝/孤立清理必须先DB终态再唯一回补。同步新建单也取场次门禁，防止与模式配置竞态；ASYNC生命周期同事务投影。重建短暂停止该场次写入，不宣称完全无影响。

[抽象模型结果](protocol-model.json)：单请求/单张票模型7个场景、17个可达状态、204条边检查通过；覆盖受理/清理两种顺序、重复效果、工作版本、旧epoch及投影GAP。**它假定锁/事务/Lua守卫正确，不执行DDL、Redis、MQ、网络或真实崩溃，不是协议实现正确性的证明**。实际跨组件故障在批次8～10执行，未用模型替代产品用例。

设计目标冻结：查询P95≤500ms，同步下单/支付P95≤1s，系统异常率<1%；正常异步30s终态、依赖恢复100在途60s；正式同云资源20/50/100/200线程，每点60+300s、至少三轮。尚未预设吞吐提升比例。
