## 1. 范围与不变量

本批补齐孤立预占封口、运行中 Redis 重建、投影缺号补齐、受控死信重放、本地持久告警和异步对账。MySQL 仍是受理、订单、资格与库存的权威事实；202 必须在可靠受理事务提交后返回。库存保持 capacity=available+reserved+sold，queued_count 等于非终态请求数且不超过 available。

沿用本机 Java 17/MySQL 和云 Redis/RabbitMQ 的混合环境。2026-10-08 用户确认公网 IP 为 118.178.253.75；脚本仍支持 TF_ECS_HOST 覆盖，并校验已有可信主机密钥。

## 2. 孤立预占与未知提交

新 Redis 回执同时保存原请求键和用于 Redis 索引的摘要；客户端不能传入 token。扫描器原子读取超期 TENTATIVE 回执，随后按 gate S → owner → 请求键 → 目录/资格 → 库存/计数取得数据库锁。

- 原键没有持久记录：写入 ADMISSION_EXPIRED/REJECTED 及确定性 RELEASE 事件，再由发件箱投影释放。
- 原键已经可靠受理或成功：保持原状态，由工作/截止扫描负责；不按临时预占年龄释放。
- 原键由另一场次请求占用：只为本候选 token 生成一次 RELEASE，不修改胜者。

封口先提交时，迟到 POST 只能重放拒绝；受理先提交时，清理只读取已受理事实。数据库确认丢失和 HTTP 响应丢失均按原键恢复，异常本身不是补库存依据。

## 3. 重建与崩溃边界

协调者在 gate X 下领取 maintenance_owner/version 和 30 秒维护租约，并提交 PAUSED。Redis 网络调用全部在数据库事务外；旧 Lua 即使迟到完成，也无法通过数据库门禁受理。

1. 冻结旧 Redis epoch，封口仍可读取的临时回执。
2. 在 gate X 下校验维护所有者/版本/期限，切换 REBUILDING 和新 epoch；迁移请求有效 epoch、增加工作版本，并把 PROCESSING 转为 RETRY_WAIT。
3. 在同一受保护事务中检查库存、两种资格、成功订单、流水、支付退款和投影历史，生成 free=A−B 的稳定快照及替代 BROKER 事件。
4. 在全新 Redis 命名空间建立暂停视图，恢复有效订单/在途 token、资格和投影水位，逐项校验映射。
5. 再次校验数据库维护版本后提交 READY，然后开启相同 Redis epoch。两个提交之间只会暂拒。

快照写入结果未知或维护者退出后，后继协调者须等待租约失效并使用新 epoch；不能对半成品视图反复增量加票。截止时间不延长。旧投影由新快照水位吸收；旧 BROKER 事件由同事务生成的替代事件接续，旧工作版本不能建单。

完整 Redis 丢失或部分 token/index 损坏时，旧回执已不能可靠恢复。系统先关闭数据库门禁，记录 REDIS_VIEW_LOST，随后整体退役旧 epoch，从数据库事实建新视图；不会根据损坏回执生成 RELEASE。旧未提交 HTTP 被 epoch 校验挡住，已提交请求仍进入快照。批次 9 缺少原请求键的旧临时回执也按不可恢复视图处理。数据库对账存在差异时保持暂停，禁止自动调整库存。

## 4. 投影与发件箱

投影只接受连续序号。出现 GAP 时从数据库按序读取最多 100 个前驱事件，包括已标记 SENT 的历史事件；仍使用幂等 Lua，不覆写绝对 free。历史缺号或关键视图缺失会关闭场次，交由对账/重建处理。

REDIS 与 BROKER 各有独立每轮最多 100 条/5 秒预算。失败事件记录退避后继续处理其他事件，避免一个场次阻塞整个队列。epoch 迁移已持久化替代事件后，旧 BROKER 事件无需继续网络投递。消息和投影仍可能重复，最终副作用由数据库终态、工作版本和 Redis 连续序号保证。

## 5. 运维入口与告警

Flyway V4 新增 tf_async_alert 和 tf_async_dead_replay，共 20 张 tf_ 表；V1～V3 不回改。告警写本地结构化日志、有限标签指标和数据库告警收件箱。数据库不可用时保留日志；本批没有接入邮件、短信或外部通知服务。

构建运行包后，在已初始化的开发环境执行：

```powershell
./scripts/async-ops.ps1 -Operation alerts
./scripts/async-ops.ps1 -Operation audit -SessionId 123
./scripts/async-ops.ps1 -Operation rebuild -SessionId 123
./scripts/async-ops.ps1 -Operation replay -EventId '00000000-0000-0000-0000-000000000000'
```

示例 ID 必须替换为实际场次/事件。脚本加载本机专用配置和既有 tf_app MQ 权限；本地临时应用关闭后台异步任务/到期扫描，仅绑定回环随机端口，操作后退出。rebuild 会暂停该 ASYNC 场次；失败时查告警并修复原因，不能手工改 READY。replay 只接受与持久发件箱完全一致的消息；有效未终态请求在原截止内重新排队，终态只确认，无再次建单。

死信重放先在数据库提交一次性重放回执和新发件箱，再 ACK 原死信。ACK 丢失后再次操作不会重复安排工作。未知/坏信封留在隔离队列；非目标消息在操作通道关闭时归还死信队列。调用返回 false 表示没有完成本次操作，不能当作已恢复。

scripts/reconcile.sql 在同一只读 REPEATABLE READ 快照中同时检查 V1 库存/订单及异步 queued_count、资格、请求归属和投影序号。audit 额外检查 Redis，并记录 epoch/seq/观测时间、重复采样和前后 DB 水位；OBSERVED_MATCH 仅表示这次在线观测一致。严格稳定切面的校验发生在暂停重建过程中，在线读数不冒充跨组件事务快照。

完整命令为 `./scripts/test.ps1 -WithAsync -Clean`。新增测试覆盖孤立封口与原键重放、跨场次候选、Redis 全量/部分丢失、正常订单生命周期跨重建、投影缺号、维护版本失效、重建结果未知、对账发现差异、真实死信重放、真实 MySQL COMMIT 传输中断，以及受理/消费和六个重建阶段的子 JVM 强杀。

强杀及协议代理只存在于 test 目录，运行包不得包含测试类。消费强杀用例在子进程就绪后设置测试夹具截止窗口，以定位提交前/后边界；维护租约失效在部分崩溃用例中通过测试库时间夹具推进。100 在途恢复实验使用真实默认 30 秒建单截止、不延长截止，以 5 个提交线程准备在途请求，计时包括 Redis 重建及终态收敛，目标 60 秒；成功与拒绝数量均保留。
